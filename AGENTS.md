# Инструкции для разработки BashMacDuler

## О проекте

BashMacDuler — приложение строки меню macOS на Swift, AppKit и SwiftUI. В репозитории нет Xcode-проекта и Swift Package: приложение собирается напрямую через `swiftc`.

## Структура

- `Sources/AppDelegate.swift` — запуск приложения, окно и значок в строке меню.
- `Sources/ContentView.swift` — SwiftUI-интерфейс списка заданий.
- `Sources/ScriptItem.swift` — модель скрипта и типы расписания.
- `Sources/ScriptStore.swift` — состояние приложения и JSON-хранилище в `~/Library/Application Support/ScriptBar` (старый путь оставлен для сохранения настроек при переименовании).
- `Sources/ScheduleCalculator.swift`, `Sources/ScriptScheduler.swift` — вычисление следующего запуска и периодическая проверка заданий.
- `Sources/ScriptRunner.swift` — запуск через `/bin/bash`, сбор stdout/stderr в лог и обновление результата.
- `Sources/NotificationManager.swift` — системные уведомления.
- `Tests/` — самостоятельные исполняемые тесты без XCTest.
- `icon.png` — исходная иконка приложения; `build.sh` преобразует её в `.icns` для app bundle.
- `build.sh`, `test.sh`, `install.sh`, `Install.command` — сборка, тесты и установка. Сборка создаёт `build/BashMacDuler.app`.

## Сборка и проверки

Нужны macOS и Xcode Command Line Tools.

```bash
./build.sh
```

Единый запуск тестов расписания и выполнения скриптов:

```bash
./test.sh
```

Запуск тестов расписания:

```bash
xcrun swiftc -swift-version 5 -parse-as-library \
  Sources/ScriptItem.swift Sources/ScheduleCalculator.swift Tests/ScheduleTests.swift \
  -o /tmp/bashmacduler-schedule-tests
/tmp/bashmacduler-schedule-tests
```

Интеграционный тест запуска скриптов (тест использует подмену `NotificationManager`, поэтому не добавляйте сюда production-файл `Sources/NotificationManager.swift`):

```bash
xcrun swiftc -swift-version 5 -parse-as-library \
  Sources/ScriptItem.swift Sources/ScheduleCalculator.swift Sources/ScriptStore.swift \
  Sources/ScriptRunner.swift Tests/RunnerTests.swift \
  -framework AppKit -framework SwiftUI \
  -o /tmp/bashmacduler-runner-tests
/tmp/bashmacduler-runner-tests
```

После изменений Swift-кода запускайте относящиеся к нему тесты; для изменений сборки — `./build.sh`. Установщик изменяет `/Applications/BashMacDuler.app` по умолчанию, поэтому не используйте его как проверку сборки.

## Архитектурные и поведенческие правила

- Сохраняйте разделение UI, состояния, вычисления расписания и выполнения процессов. Не помещайте запуск процессов или сериализацию в SwiftUI-представления.
- `ScriptStore` — источник состояния для интерфейса. Его `@Published`-свойства и завершение UI-операций должны обновляться на главном потоке; длительный процесс выполняйте вне главного потока.
- Для планирования используйте `Calendar` и локальную временную зону пользователя, а не арифметику фиксированных 24/168 часов. Расчёты должны оставаться детерминированно тестируемыми через передаваемый `Calendar`.
- Поддерживаются ежедневные, еженедельные, ежемесячные расписания (выбранные дни 1–31) и одноразовые выбранные календарные даты. Не нормализуйте недостающие дни месяца на другой день; пропускайте месяц, в котором такого дня нет.
- `ScheduleDate` хранит год, месяц и день без времени, чтобы выбранные календарные даты не сдвигались при смене временной зоны. Для вычисления времени запуска используйте переданный `Calendar`.
- Перед запуском задания обновляйте его расписание так, чтобы частый тик планировщика не запускал один и тот же просроченный запуск повторно.
- Запускайте пользовательские файлы через `Process` с отдельными аргументами (`executableURL` и `arguments`); не собирайте командную строку shell-конкатенацией. Рабочая директория — каталог скрипта.
- Сохраняйте stdout и stderr в лог и фиксируйте код завершения. Ошибки чтения/записи настроек и запуска должны оставаться диагностируемыми; не превращайте ошибки в молчаливый успех.
- Учитывайте обратную совместимость JSON-модели `ScriptItem` при изменении сохраняемых полей или enum-значений. Добавляйте миграцию/значения по умолчанию для существующих данных.
- Проверяйте доступность выбранного файла и корректность компонентов расписания на границе ввода. Пути файлов обрабатывайте как данные, не как фрагменты shell-команды.
- Не редактируйте `build/BashMacDuler.app` вручную: это производный артефакт `build.sh`. Не удаляйте и не заменяйте пользовательские данные при сборке/установке без явной проверки целевого пути.

## Стиль изменений

- Следуйте существующему стилю Swift: понятные имена, небольшие методы и минимальные изменения без сторонних зависимостей.
- Пользовательские сообщения и документацию пишите по-русски, используя название приложения BashMacDuler.
- Для поведения, зависящего от времени, добавляйте тесты на границы дня/недели, прошедшее время и переходы летнего времени; избегайте тестов, зависящих от текущей даты или часового пояса машины.
- Обновляйте `readme.md`, если меняются возможности, ограничения, сборка или установка.

## Рабочий процесс

- Перед изменениями изучите связанный код и тесты; сохраняйте уже имеющиеся пользовательские изменения.
- После изменения Swift запустите соответствующие тесты из `Tests/`. Запускайте полную сборку, если затронуты исходники приложения, `Info.plist` или `build.sh`.
- Не используйте `install.sh` для проверки: по умолчанию он заменяет приложение в `/Applications`. Для установщика отдельно проверяйте в коде все пути, передаваемые в удаление или замену; не допускайте удаления произвольных каталогов.
- Проверяйте `git status` после сборки: `build/BashMacDuler.app` и `.DS_Store` — локальные/производные файлы, не редактируйте их вручную и не включайте в изменения без явной необходимости.
- Не добавляйте новые зависимости и систему сборки без необходимости; если workflow меняется, одновременно обновите эту инструкцию и `readme.md`.

## Инварианты поведения

- Расписание локальное: день недели соответствует `Calendar.current`, время — локальному времени пользователя. Для тестов передавайте календарь с фиксированным часовым поясом.
- Если приложение было закрыто или компьютер спал в момент запуска, при следующей проверке выполняется один пропущенный запуск; далее расписание рассчитывается от текущего времени. Не запускайте пачку повторов за каждый пропущенный интервал.
- После запуска по выбранным датам удаляйте все даты, прошедшие к моменту запуска; это сохраняет политику одного catch-up запуска после долгого простоя.
- Один и тот же скрипт не должен выполняться параллельно сам с собой; разные скрипты могут выполняться одновременно.
- JSON-файл и логи находятся в Application Support. Не удаляйте и не перезаписывайте существующие настройки при ошибке чтения, миграции или сохранения; сохраняйте диагностическую информацию.
- Логи содержат пользовательский вывод и могут со временем занимать место. Если меняется их хранение или очистка, задайте и документируйте политику хранения, не удаляя свежие логи и не нарушая ссылку на последний запуск.
- В тестах запуска используйте подмену `NotificationManager` из `Tests/RunnerTests.swift`; production-уведомления не должны требоваться для успешного выполнения тестов.
- Срок хранения логов — 30 дней; при очистке сохраняйте логи, на которые ссылается `lastLogPath`.
